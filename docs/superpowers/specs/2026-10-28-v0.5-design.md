# v0.5: parts and wholes, built on the cortex, in real video — design

## Intent

v0.4 made the world an editable scene graph, but only for sprites. On the webcam it found a person as five unrelated pieces. It compared raw brightness, did not handle a moving camera, and its adult failed permanence and curiosity. The user asked for four things in one release ("1-4 one shot for 0.5"):

1. **Parts and wholes:** pieces that move together form a parent object. A person is a node whose parts are head, hand and shoulder.
2. **Built on the cortex:** objects are described in the cortex's code, not in raw pixels.
3. **Real video with a moving camera:** the camera's own motion is registered away, so that only objects move.
4. **Fix permanence and curiosity.**

All calls below are Claude's, made without further questions, at the user's request.

## Rules

v0.4's rules hold. Learning is local only, protocols are written before measuring, and both runs and failures are reported. Protocols 9 and 11 are re-run unchanged, on new test seeds: 3020–3039 and 5020–5039. Their v0.4 seeds have been looked at during development.

## Architecture (Claude's calls)

### Appearance in the cortex's code

The graph works on a stack of channels per pixel:
- luminance, for display and editing only, weight 0 in matching;
- the cortex's retina code: ON and OFF centre-surround contrast, divisively normalised, from `cortex/retina.py` at the graph's resolution;
- V1 activity: the v0.3 phase 1 adult's V1, settled on the same frame, summed over cells and upsampled.

Matching, masks and backgrounds use the code channels; edits and the picture use luminance. Contrast normalisation makes the code largely independent of overall lighting. `--front luminance` keeps v0.4's behaviour as the ablation.

### Parts and wholes

Every pair of object nodes carries a binding strength *b*. Each frame it moves toward the common fate of the pair, a Hebbian product of how well their recent displacements agree and how close they are, with a time constant of about one second. Nodes bound above 0.5, taken transitively, form a **group**: a parent node with a "part of" edge from each child.
- Deleting or moving a group applies to all its parts.
- The JSON gains `groups`.
- The page draws a group as a hull around its parts; clicking a hull edits the whole.

Rigid merging stays as it was: parts that touch and move identically still become one node. Binding is for parts that move together but not rigidly, such as limbs.

### Camera motion

`VideoGraph` wraps the scene graph like the eye graph does: a canvas larger than the view, and registration of each frame against it. Here there is no command; every global shift is the camera's. The canvas is held fixed in the world and the view moves over it, so the background stays put and only objects move. For the expectation of the next frame, the graph predicts only what it explains: object nodes in view, and the background where it is confident. Elsewhere it predicts the last frame.

### Permanence

When a node's visibility falls while it moves into a region of confident, still background, that region is taken to be in front of it at once: an occluder is learned on entry, not after the node is lost. Low-contrast objects should also benefit from the contrast-normalised code.

### Curiosity

The gaze gains a **progress memory** on the canvas: the learning progress each fixation brought, written where it was made, and decaying slowly.
- It starts optimistic, at 1, everywhere: unexplored places are presumed to teach.
- Wherever the prediction error jumps (something new appears), it is raised again.
- The feature "progress here" joins the others under the same three-factor rule.

Noise brings no progress, so it is learned to be worthless there and only there. A newcomer raises its place again.

## New protocols (written before measuring)

- **13, parts and wholes:** articulated creatures in the sprite world. Each has a torso and one or two limbs that swing about the torso as it moves. Do the groups match the creatures, and does deleting a creature beat a bitmap?
- **14, lighting:** the sprite world under slow global changes of illumination and gain. Does tracking survive with the cortex code, and fail with luminance?
- **15, real video:** UCF101 test-split clips. Does the graph's expectation of the next frame beat repeating the last frame, and does camera registration help?

### Amendment after development, before any test measurement (2026-10-28)

On the development seeds of protocol 14 (700–707), V1's learned code made a poor appearance for objects:

| Code | Constant light: IoU, counts right | Changing light: IoU, counts right |
|---|---|---|
| Brightness | 0.83, 0.93 | 0.31, 0.00 |
| V1's rendering of the retinal code | 0.26, 0.49 | 0.26, 0.62 |
| Normalised, σ = 24 (local z-score) | 0.91, 0.90 | 0.91, 0.99 |

V1's code is contrast: it describes edges, so a smooth object's inside looks like the background, and only outlines are found. Mixing V1 into the normalised code lowered the counts every time.

v0.5 therefore matches objects on the **normalised code**: the retina's divisive normalisation applied at the scale of surfaces (`NormalisedFront`). This is innate, not learned. V1's code stays as a reported third condition in protocol 14, so the negative finding is measured on the test seeds too. "Built on the cortex" holds for the principle (normalisation), not for the learned features.

### Second amendment, before any test measurement (2026-10-28)

- **Which code where:** under constant light, the sprite-world protocols (9, 11, 13) run on brightness. On development seeds 3100–3119, the normalised code lowered permanence: 0.20 of hidden objects kept, against 0.65 on brightness. The bright screen dominates the local normalisation around it. The normalised code is used where the light changes (protocol 14) and on video (protocol 15, the live camera).
- **Permanence:** two remedies were tried on development seeds and both made it worse:
  - the normalised code (0.20 kept);
  - pure prediction while visibility falls (0.55 kept).
  Neither is in v0.5. Protocol 9's re-run measures v0.5 with the parts-and-wholes changes only.
- **Curiosity:** the progress memory is the place's own learned value, added to the weighted features, rather than one more weighted feature. As a feature, its weight came out negative (−0.15): early fixations at optimistic places taught little. It starts at 0.5, about what exploring an unknown place brings.
- **Camera:** each frame's global shift is estimated from the frames themselves (phase correlation) and handed to the eye graph as its self-motion. Registration against the canvas corrects what remains, and the canvas is recentred under long pans. The expectation moves with the camera to the sub-pixel. On development (the sample clip and UCF101 validation), shifting the last frame with the camera alone reached 0.99; the graph reached 1.01.
